## 2. 적용 원칙

- 상위 문서의 모듈 책임 경계표(4.1), 핵심 데이터 계약(4.2), 상태 분할(4.3), 폴더 구조(8절), asmdef 의존 방향, 단계 순서를 그대로 따른다. 이 문서가 정하는 것은 실행 순서뿐이다.
- 원작 수치가 필요한 값은 코드에 상수로 넣지 않고 `TuningPending`으로 표기한다. 테스트용 임시값과 원작 비교를 통과한 값을 구분한다.
- 에디터 GUI가 필요한 작업(씬 저장, 프리팹 구성, URP 설정 재연결, 그리드 굽기)과 파일로 처리 가능한 작업(스크립트, asmdef, ScriptableObject 정의, manifest, 레이어 등록)을 분리한다. 파일로 가능한 작업을 먼저 끝내 에디터 작업 횟수를 줄인다.
- 기존 `Assets/Scenes/SampleScene.unity`와 `Assets/Settings/`는 삭제하지 않는다. `_DCG` 아래에 새 씬을 만들고 기존 자산은 그대로 둔다. 삭제 여부는 URP 복구 후 별도 결정으로 기록한다.
- 패키지 버전은 임의로 고르지 않는다. manifest에 선언한 뒤 `6000.5.5f1` 에디터가 해석한 결과를 `packages-lock.json`에서 확인하고 고정한다.

## 3. 단계별 적용

### 0-A. 프로젝트 복구 — 선행 블로커

코드 작성 전에 처리한다.

1. `Packages/manifest.json`에 Input System, URP, AI Navigation, Test Framework를 직접 의존성으로 선언한다.
2. 에디터를 1회 기동해 임포트 로그를 확인한다. URP 에셋과 `GraphicsSettings` 참조가 복구되는지, `InputSystem_Actions.inputactions`가 정상 로드되는지 확인한다.
3. 해석된 버전을 `packages-lock.json`에서 확인하고 고정한다.
4. Netcode for GameObjects는 이 시점에 설치하지 않는다. 상위 문서 7.1이 NGO를 첫 검증 후보로만 두었고 4단계 전까지 필요하지 않다. 미리 설치하면 Gameplay가 NGO를 참조하는 순환 의존이 생기기 쉽다. 8절의 의존 방향 규칙을 지키기 위해 의도적으로 늦춘다.

완료 조건: 콘솔 에러 0, SampleScene 플레이 진입, 빈 상태 빌드 성공.

### 0-B. 골격 생성

상위 문서 8절 구조를 그대로 생성한다.

- `Assets/_DCG/` 이하 폴더 트리를 상위 문서에 적힌 그대로 만든다.
- asmdef 7개를 만든다. `DCG.Core` → `DCG.Gameplay` → `DCG.Classes`, 그리고 `DCG.Presentation`, `DCG.Networking`, `DCG.Bootstrap`, 테스트·에디터용. 의존 방향은 단방향으로 유지한다. `DCG.Networking`은 이 시점에 빈 asmdef로 두고 NGO를 참조하지 않는다.
- 물리 레이어 `World`, `CharacterBody`, `Hurtbox`, `Projectile`, `NavigationSurface`, `LocalViewModel`을 `TagManager.asset`에 등록하고 충돌 매트릭스를 설정한다.
- Input Actions를 `_DCG/Input/DCGControls.inputactions`로 새로 만들고 맵을 `UI`, `Graves`, `Vendetta`, `Rifle`, `Sniper`로 분리한다. 기존 `InputSystem_Actions`는 유지하되 사용하지 않는다.
- 상위 문서 3절의 원작 명세 표를 빈 템플릿으로 `docs/`에 만든다. 4직업 × 명세 항목을 전부 `TuningPending`으로 채운다. 이 표는 사용자가 원작 영상과 입력 기록으로 채워야 하는 입력이며 추측으로 채우지 않는다.

완료 조건: 빈 asmdef 구성으로 컴파일 통과, 네 직업의 확정·미확정 항목이 표로 구분됨.

### 1. 공통 기반

- `Core`: `ActorId`, `CommandEnvelope`, `MoveToCommand`, `TargetCommand`, `DirectControlFrame`, `ActionCommand`, `ActorSnapshot`, `CombatEvent`를 상위 문서 4.2의 필드대로 정의한다. Camera, Animator, GameObject 참조를 넣지 않는다.
- `Gameplay`: `ActorSimulation`(틱 순서 단일 소유), `CharacterMotor`(CharacterController 기반 후보), `IMovementPolicy`, `HealthState`, `DamageSystem`, `ICommandGateway`와 `LocalSession` 구현.
- 상태는 상위 문서 4.3대로 생존·이동·행동 3분할로 둔다. 하나의 거대한 enum으로 만들지 않는다.
- `ControlLab.unity`를 만들고, 입력 없이 테스트 명령으로 이동·피해·사망을 재현하는 EditMode/PlayMode 테스트를 작성한다.

완료 조건: 입력·카메라·네트워크 코드 없이 테스트만으로 이동·피해·사망 재현.

### 2. 그레이브즈 최소 루프

- `Navigation`: `GridGraph`(에디터 굽기 툴 포함), `AStarPathService`(요청 번호로 오래된 결과 폐기), `PathFollower`.
- `Classes/Graves`: `GravesOrderController`, `TargetTracker`, `TopDownRig`.
- 클릭 → UI 클릭 제외 → 지면/타깃 판별 → 명령 → 경로 → Motor 순서로 연결한다. `NavMeshAgent`로 대체하지 않는다.

완료 조건: 장애물 우회, 연속 클릭 시 경로 교체, 이동·공격·공격이동·정지 전환 정상.

### 3~8단계

상위 문서 10절의 표를 그대로 따른다. 다만 두 항목의 착수 시점을 앞당긴다.

| 항목 | 상위 문서 위치 | 변경 후 시점 | 이유 |
|---|---|---|---|
| 디버그 오버레이 | 11절, 8단계 품질 보강 | 1단계 종료 시점 | 4단계 네트워크 계측이 오버레이 없이는 판정 불가 |
| RTT·패킷 손실 주입 도구 | 7.4 검증 조건 | 3단계 진행 중 | 4단계가 재선택 게이트인데 측정 도구를 그때 만들면 게이트가 형식화됨 |

이 두 항목은 단계 순서를 바꾸는 것이 아니라 준비 시점만 당기는 것이다. 각 단계의 완료 조건은 상위 문서 그대로 유지한다.

## 4. 선행 결정 항목

0-A에서 렌더 파이프라인 방향이 갈린다. 상위 문서는 "기존 샘플 씬의 렌더 파이프라인 설정도 확인한다"까지만 정하고 결론을 두지 않았다.

- 권고: URP 복구. `Assets/Settings`의 에셋과 `GraphicsSettings`가 이미 URP 전제로 저장되어 있어 복구 쪽이 변경 범위가 작다.
- 대안: Built-in으로 내리고 URP 에셋을 제거. 이 경우 `GraphicsSettings`와 `Assets/Settings` 정리가 필요하며 기존 틀을 바꾸는 결정이므로 별도 기록이 필요하다.

## 5. 남은 미결정

상위 문서 12절의 6개 항목은 그대로 유효하다. 실측으로 확인된 두 항목을 추가한다.

7. `activeInputHandler: 1`이 의도한 설정인지, Input System 패키지가 제거되며 남은 잔재인지.
8. `SampleScene`과 `Assets/Settings`를 유지할지, `_DCG` 정착 후 제거할지.

## 6. 첫 실행 묶음

0-A(패키지 복구) → 0-B(폴더·asmdef·레이어·입력맵) → 1단계(Core/Gameplay + ControlLab).

이 묶음이 끝나면 프로젝트가 에러 없이 실행되고, 명령 해석·이동·전투·피해가 분리된 상태에서 이후 직업과 네트워크를 붙일 수 있는지 확인한다. 화면상 캐릭터가 움직이는 것만으로 완료로 처리하지 않는다.
