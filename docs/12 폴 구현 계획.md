# 12 폴(철권) 구현 계획

작성일: 2026-09-17. 대상: DCG-Project / Unity 6000.5.5f1.

철권 폴 피닉스를 기준으로 격투 조작 캐릭터를 추가하기 위한 계획이다. 구현 전 단계 문서이며, 아래 수치와 기술 목록은 원작 확인 전까지 TuningPending으로 취급한다.

## 선행 확인 사항

- 범위 충돌: `05 Unity 개발 계획.md` 1절과 `07 원작 조작 명세.md`는 격투가·철권 조작을 범위에서 제외했다. 구현 착수 전에 두 문서의 범위를 수정한다.
- 틱 속도: 현재 `ProjectSettings/TimeManager.asset`의 Fixed Timestep은 0.02(50Hz)다. 철권은 60프레임 기준이므로 프레임 단위 판정이 어긋난다. 전역 설정은 바꾸지 않고 격투 루프가 자체 60Hz로 진행한다(아래 구조 참조).

## 1. 키 매핑

| 키 | 철권 표기 | 의미 |
| --- | --- | --- |
| U | 1 | 왼손 (LP) |
| I | 2 | 오른손 (RP) |
| O | 1+2 | 양손 매크로 |
| J | 3 | 왼발 (LK) |
| K | 4 | 오른발 (RK) |
| L | 3+4 | 양발 매크로 |
| WASD (제안) | 방향 | 캐릭터 기준 f/b/u/d로 변환 |

규칙:
- O·L은 별도 버튼이 아니라 1+2, 3+4 비트를 동시에 켠다. U+I 동시 입력과 O는 동일하게 처리한다.
- 동시 입력 허용 간격: 서로 다른 프레임에 눌린 버튼도 N프레임 안이면 동시 입력으로 판정한다(초기값 2프레임, 조정 대상). 1+3(U+J), 2+4(I+K), 2+3(I+J), 1+2+3+4(O+L)을 모두 지원한다.
- 입력 리더는 좌/우 원시 방향만 보낸다. 시뮬레이션이 1-1의 방향 규칙으로 f/b로 변환하므로 좌우가 바뀌어도 커맨드가 유지된다.
- 반대 방향 동시 입력(A+D)은 중립으로 정리한다(SOCD 정리).
- 키보드 고스팅: 저가 키보드는 WASD 2키와 UIOJKL 2~3키 동시 입력이 누락될 수 있다. 초기 테스트에서 확인한다.

## 1-1. 방향 고정 규칙

2026-09-17 사용자 확정.

- 캐릭터는 상대가 어디에 있든 항상 상대를 향해 횡방향(측면 대치)으로 고정된다. 자유 회전은 없다.
- 좌우 판정은 맵 기준 동서(X축)로 한다.

| 맵 위치 | 판정 | 앞(f) | 뒤(b) |
| --- | --- | --- | --- |
| 상대가 동쪽, 플레이어가 서쪽 | 일반 위치 | D | A |
| 상대가 서쪽, 플레이어가 동쪽 | 반대 위치 | A | D |

구현 규칙:
- 매 프레임 두 캐릭터의 X좌표를 비교해 `Side`(Normal / Reversed)를 정한다. 두 캐릭터는 항상 서로 반대 Side를 갖는다.
- 바라보는 방향(Facing)은 매 프레임 상대 위치로 즉시 맞춘다. 공격 중에도 몸 방향 고정이 풀리지 않는다. 기술별 추적 제한이 필요해지면 MoveData 속성으로 따로 정의한다.
- X좌표가 같거나 차이가 아주 작을 때(허용 오차 이내)는 직전 Side를 유지한다. 횡이동으로 남북에 겹칠 때 좌우가 매 프레임 뒤집히는 것을 막는다. 허용 오차는 TuningPending.
- Side 전환은 캐릭터가 중립·이동 상태일 때 적용한다. 공격·경직·공중 상태 중에는 전환을 보류했다가 해당 상태가 끝나는 프레임에 적용한다(초기 제안, 조작 확인 후 확정).
- InputBuffer에는 원시 좌/우를 저장하고, 각 프레임을 그 프레임의 Side로 f/b 변환해 파서에 넘긴다. qcf 입력 도중 Side가 바뀌어도 이미 입력한 프레임의 해석은 바뀌지 않는다.
- W/S(u/d)는 Side와 무관하다. u/d 톡 입력 횡이동의 실제 이동 방향은 두 캐릭터 축에 수직인 방향으로 계산한다.
- 카메라는 좌우 판정과 화면이 일치하도록 맵 남쪽에서 북쪽을 바라보는 방향을 기준으로 둔다. 이렇게 하면 화면 오른쪽이 항상 동쪽이다. 두 캐릭터가 남북으로 크게 벌어질 때의 카메라 처리는 3D 횡이동 범위 결정(5절 3번)과 함께 정한다.
- EditMode 테스트: 동서 위치별 f/b 변환, X좌표 동일 시 Side 유지, 입력 도중 Side 전환 시 기존 프레임 해석 유지.

## 2. 구조

Vendetta와 같은 입력 리더 → `LocalSession` → 정책 흐름을 따른다. 단, 기술 판별은 입력 리더가 아니라 시뮬레이션이 한다. 입력 리더는 매 프레임 원시 입력만 보낸다. 이후 네트워크와 입력 재생 테스트를 위한 결정이다.

```
FighterInputReader (Classes/Paul)
   └ 매 프레임 FightInputFrame { Direction(1~9), Held, Pressed, Released }
        ↓ LocalSession (기존 발신자·순서 검증)
InputBuffer (최근 60프레임 링 버퍼)
   ↓
CommandParser: "d,df,f+2" 표기를 우선순위 순서로 매칭
   ↓
FighterStateMachine: 서기/앉기/대시/백대시/횡이동/점프/공격(발동·판정·후딜)/히트경직/가드경직/다운/자세
   ↓
FightResolver: 두 캐릭터를 같은 프레임에 판정 (상단/중단/하단/잡기, 가드, 카운터, 상쇄)
   ↓
기존 DamageSystem / HealthState 재사용
```

### 변경·추가 항목

- Core(`Contracts.cs`): `CommandType.FightInput`, `FightButtons` 플래그(1/2/3/4), `FightInputFrame` 구조체 추가. 기존 `ControlButtons`는 다른 직업의 입력 검증에 쓰이므로 섞지 않는다.
- Gameplay/Fighting(순수 C#): `InputBuffer`, `CommandParser`, `FrameClock`. MonoBehaviour 의존 없이 EditMode에서 합성 입력 프레임으로 검증한다.
- `MoveData` ScriptableObject: 커맨드 문자열, 발동/판정/후딜 프레임, 판정 위치(상단·중단·하단·잡기), 피해, 가드·히트·카운터 시 이득 프레임, 이어치기 입력 허용 구간, 자세 전환, 속성(파워크래시, 상단 회피 등). 폴의 기술은 `Paul_Moves` 묶음으로 관리한다.
- 60Hz 루프: 전역 설정은 유지한다. `PaulLab`에서만 격투 루프가 1/60초 누적으로 프레임을 진행하고, Input System을 `ProcessEventsManually`로 두고 매 프레임 `InputSystem.Update()`를 호출한다. 입력 1회가 시뮬레이션 1프레임에 대응하므로 d→df→f 순서가 렌더 프레임 수에 따라 뭉개지지 않는다.
- 동시 판정: 현재 `ActorSimulation.Step`은 캐릭터별로 `AfterMove`를 호출해 먼저 처리된 쪽이 먼저 판정된다. 상쇄(동시 타격)를 위해 두 캐릭터를 함께 진행하는 `FighterMatch` 루프를 둔다.
- Presentation: 두 캐릭터 중점을 보는 측면 카메라(1-1 규칙에 따라 맵 남쪽 기준), 입력 기록 HUD(철권 연습 모드 방식), 이득 프레임 표시.
- 연습 상대: 입력 녹화·재생 더미(전부 가드 / 앉아 가드 / 녹화 재생).

## 2-1. 피격 결과(상대 상태 변화) 명세

폴의 기술은 피해만 주는 것이 아니라 상대의 상태를 바꾼다. 오른 어퍼로 띄우기, 공격 중인 상대를 맞혔을 때만 발생하는 카운터 효과 등이다. 이 결과를 기술마다 데이터로 명세하고, 공격자 기술이 결과를 정하며 피격자 상태 머신이 그 결과를 실행한다.

### 역할 분리

- `MoveData`(공격자): 상황별로 상대에게 어떤 결과를 줄지 정의한다.
- `FightResolver`: 피격자의 현재 상태를 보고 어떤 상황 결과를 적용할지 고른다.
- `FighterStateMachine`(피격자): 선택된 결과를 받아 경직·공중·다운 등의 상태로 전환하고 프레임 단위로 실행한다.
- 결과 판정은 프레임 루프 안에서 두 캐릭터 모두 판정한 뒤 한 번에 적용한다(상쇄 처리 포함).

### 피격자 상태 태그

Resolver가 결과를 고를 때 읽는 피격자 상태다.

| 태그 | 의미 | 결과 선택에 미치는 영향 |
| --- | --- | --- |
| Standing / Crouching | 서기 / 앉기 | 상단 회피, 하단 가드 가능 여부 |
| Guarding(High/Low) | 서서 가드 / 앉아 가드 | 판정 위치와 비교해 가드 성립 |
| AttackStartup / AttackActive / AttackRecovery | 공격 발동 / 판정 / 후딜 | 카운터 히트 성립 여부 |
| Hitstun / Blockstun | 피격 경직 / 가드 경직 | 콤보 성립, 가드 불가 |
| Airborne(Juggle) | 띄워진 상태 | 공중 히트 결과 사용, 공중 콤보 보정 |
| Grounded(FaceUp/FaceDown, 머리 방향) | 다운 | 다운 히트 가능 기술만 적중 |
| Backturned | 등 돌림 | 가드 불가, 별도 결과 |
| Sidestep | 횡이동 중 | 추적(호밍) 속성 없는 기술 회피 |
| Crushing(High/Low) | 기술의 상단/하단 회피 프레임 | 해당 판정 공격 회피 |
| PowerCrush | 파워크래시 판정 프레임 | 상·중단을 맞아도 기술 유지(피해는 받음) |

### 결과 선택 순서 (Resolver)

1. 잡기 판정: 잡기면 잡기 풀기 입력 구간을 확인한다.
2. 회피: 피격자의 Crushing / Sidestep 상태와 공격의 판정 위치·추적 속성을 비교한다.
3. 가드: 피격자의 가드 자세와 판정 위치(상단·중단·하단)를 비교한다. 성립하면 `OnBlock`.
4. 파워크래시: 성립하면 피해만 적용하고 피격자 기술은 유지한다.
5. 공중 / 다운: 피격자가 Airborne이면 `OnAirborneHit`, Grounded면 `OnGroundHit`(없으면 헛침).
6. 카운터 히트: 피격자가 카운터 성립 상태면 `OnCounterHit`, 정의가 없으면 `OnHit` + 카운터 피해 보정.
7. 그 외: `OnHit`.

카운터 히트가 성립하는 피격자 상태(발동만인지, 판정·후딜 포함인지)와 상쇄 시 양쪽 결과 규칙은 원작 확인 후 13 문서에 기록하고 전역 설정으로 둔다. 확인 전까지 AttackStartup·AttackActive만 성립으로 둔다(TuningPending).

### MoveData 결과 필드

```
MoveData
  hitLevel            High / Mid / Low / SpecialMid / Throw
  damage, counterDamageBonus
  properties          HighCrush(프레임 구간), LowCrush(구간), PowerCrush(구간), Homing, Tornado, WallSplat …
  onHit               HitOutcome
  onCounterHit        HitOutcome (선택, 비우면 onHit 사용)
  onAirborneHit       HitOutcome (공중 콤보용, 선택)
  onGroundHit         HitOutcome (다운 히트 가능 기술만)
  onBlock             BlockOutcome

HitOutcome
  reaction            아래 반응 종류
  advantageFrames     공격자 기준 이득 프레임
  stunFrames          경직 길이 (Stagger/Crumple 등)
  launch              띄우기 높이·수평 속도 (Launch 계열)
  knockdown           FaceUp / FaceDown, 머리 방향
  turnDefender        등 돌림 여부
  pushback            밀려나는 거리
  juggleCost          공중 콤보 보정 소모량

BlockOutcome
  advantageFrames, pushback, guardBreak(가드 붕괴 여부)
```

### 반응(reaction) 종류

| 반응 | 설명 | 폴 예시(원작 확인 필요) |
| --- | --- | --- |
| Stagger | 서서 짧은 경직, 이득 프레임만 발생 | 원투 계열 잽 |
| CrouchStagger | 앉은 채 경직 | 하단 기술 히트 |
| Launch | 공중으로 띄움, 공중 콤보 시작 | 오른 어퍼(df+2 등) |
| CounterLaunch | 카운터 히트일 때만 띄움, 일반 히트는 Stagger | 카운터 전용 띄우기 기술 |
| Knockdown / BlowAway | 즉시 다운 또는 날려서 다운 | 붕권(qcf+2) |
| Crumple | 주저앉는 경직, 추가타 가능 | 카운터 히트 강공격 |
| Spin / Twist | 회전 경직, 등 돌림 발생 가능 | 카운터 히트 옆치기 |
| Tornado(Screw) | 공중 상대를 회전시켜 콤보 연장 (철권 8) | 공중 콤보 연결기 |
| WallSplat / WallBound | 벽에 붙거나 튕김 | 6단계 이후 |
| GuardBreak | 가드해도 경직을 강제 | 해당 속성 기술 |
| ThrowHit | 잡기 성공 연출과 고정 결과 | 1+3 / 2+4 |

위 예시 칸의 커맨드와 결과는 구조 설명용이다. 실제 폴 기술별 결과는 원작 인게임 커맨드 리스트와 연습 모드(히트·카운터·가드 이득 프레임 표시)로 확인해 13 문서에 기록한다.

### 13 문서 기술 표 양식

| 커맨드 | 판정 | 발동 | 가드 시 | 히트 시(반응 / 이득) | 카운터 시(반응 / 이득) | 공중 히트 | 다운 히트 | 속성 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 예: df+2 | 중단 | ?F | ? | Launch / - | ? | ? | 불가 | - |
| 예: qcf+2 | 중단 | ?F | ? | BlowAway / ? | ? | ? | ? | ? |

`?`는 원작 확인 전 값이다. 표가 채워지면 `Paul_Moves` MoveData 에셋으로 옮긴다.

### 테스트

- EditMode: 피격자 상태별 결과 선택 순서(가드 우선, 회피, 카운터, 공중·다운 분기).
- PlayMode: 오른 어퍼 히트 → 피격자 Airborne 전환 → 추가타 `onAirborneHit` 적용.
- PlayMode: 발동 중인 상대를 맞히면 `onCounterHit`, 서 있는 상대는 `onHit`.
- PlayMode: 상쇄 시 양쪽 결과가 같은 프레임에 적용되는지, 파워크래시 중 피해만 받고 기술이 유지되는지.

| 3 | 프레임 상태 머신, MoveData, 피격자 상태 태그, Resolver 결과 선택(가드·히트·카운터), Stagger·Knockdown 반응, 연습 더미 | EditMode: 결과 선택 순서 / PlayMode: 이득 프레임, 카운터 분기 |
| 4 | 이어치기 입력 허용 구간, 커맨드 기술(qcf/qcb), 자세, 상단·하단 회피와 파워크래시 속성 | EditMode + 사람 조작 |
| 5 | Launch·공중 콤보 보정, Crumple·Spin·등 돌림, 다운·다운 히트·기상, 잡기와 잡기 풀기 | PlayMode: 띄우기 → 공중 히트 |
| 6 | 벽, 히트/레이지 시스템, 네트워크 | 별도 설계 |

## 4. 구현 가능한 커맨드 범위

### 쉬움 — 1차 파서로 바로 가능
- 단일 버튼, 방향+버튼: 1, 2, 3, 4, d+4, df+1, b+2, f+2
- 동시 입력: 1+2(O), 3+4(L), 1+3/2+4(잡기), 2+3(철권 8 히트 버스트), 1+2+3+4
- 이어치기: 1,2 / 1,2,4 등 입력 허용 구간 안의 연속 입력
- 이동: f,f 대시, b,b 백대시, u/d 톡 입력 횡이동, d 유지 앉기, u 유지 점프
- 방향 유지 구분: b 유지 서서 가드, db 유지 앉아 가드

### 중간 — 설계가 맞으면 가능, 폴의 핵심
- 방향 돌리기: qcf(d,df,f)+2 붕권(Phoenix Smasher), qcb(b,db,d) Sway 자세 진입. 키보드에서는 S → S+D → D 순서이므로 허용 프레임을 너그럽게 잡는다.
- 자세 파생기: 자세 상태에서만 유효한 커맨드 표를 따로 둔다(예: `SWAY 1`).
- ws(일어서며), FC(완전히 앉은 상태), 앉으며 대시 계열
- 버튼 유지·충전 [2], 딜레이 이어치기
- 레이지 아츠(df+1+2), 잡기 풀기(1 또는 2 일치)
- 피격 결과 분기: 히트/카운터/가드/공중/다운별 상대 상태 변화(2-1). 띄우기, 카운터 전용 띄우기, 주저앉기, 회전 경직

### 어려움 — 가능하지만 비용이 큼
- 저스트 프레임 입력: 60Hz 고정 샘플링 전제. 파서로는 가능하나 키보드 체감을 맞추기 어렵다.
- 공중 콤보 보정, 토네이도, 다운 후 기상·낙법 공방
- 벽 꽝·바닥 부수기, 3D 횡이동에 대한 추적(호밍) 판정
- 애니메이션 기반 타격 판정: 모델·애니메이션 전까지 캡슐/박스 타이밍으로 대체

### 현재 구조로는 권장하지 않음
- 롤백 넷코드: 05 문서는 NGO 서버 권위 구조다. 격투 게임 수준의 온라인 품질이 필요하면 별도 아키텍처 결정이 필요하다. 오프라인·로컬 대전은 문제없다.
- 기억에 의존한 원작 프레임 데이터 입력: 프로젝트 원칙상 추측하지 않는다. 붕권 외의 세부 사항(Sway 파생기, 입력 허용 구간 등)은 철권 인게임 커맨드 리스트와 연습 모드 이득 프레임 표시로 확인해 13 문서에 기록하고, 그때까지 TuningPending으로 둔다.

## 5. 결정 필요 사항

1. 방향키: WASD(오른손 UIOJKL과 분리, 권장) 또는 방향키
2. 기준 버전: 철권 7 또는 8. 8이면 히트 시스템이 추가되어 범위가 늘어난다.
3. 공간: 3D 횡이동 포함 여부, 또는 첫 실습은 2D 평면으로 제한
4. 통합 방식: 독립 `PaulLab` 씬(Vendetta 방식, 권장) 또는 기존 1대1 전장에 통합
