# 14 통합 컨트롤 허브 계획

작성일: 2026-09-19. 대상: DCG-Project / Unity 6000.5.5f1.

지금까지 각 직업은 독립 실습 씬으로 구현했다(ControlLab, VendettaLab, RifleLab, SniperLab, PaulLab).
이 문서는 그 다섯 조작을 **하나의 씬 ControlHub.unity**에 모으는 작업 계획이다. 구현 전 단계 문서이며, 여기서 정하는 것은 구조와 순서다.

2026-09-19 사용자 확정 방향:
- 공간: 구역 분리나 Additive 로딩이 아니라 **완전 통합 단일 환경**. 모든 직업이 같은 맵을 쓴다.
- 틱: **전역 60Hz 통일**. `TimeManager`의 Fixed Timestep을 0.02에서 1/60으로 바꾼다.
- 전환: **직업 선택 메뉴 화면**. 진입 시 선택 화면 → 선택 후 플레이.

단순히 오브젝트를 한 씬에 모으면 깨지는 지점을 먼저 정리한다. 이 목록이 실제 작업 항목이 된다.

| --- | --- | --- | --- |

## 3. 전역 60Hz 전환

확정된 방향이지만 부작용이 있으므로 **0단계에서 단독으로 먼저 처리하고 기존 5개 랩을 회귀 검증한 뒤 다음으로 넘어간다.**

변경 내용:
- `ProjectSettings/TimeManager.asset`의 Fixed Timestep을 `0.02` → `0.016666668`. **2026-09-20 적용 완료.**
- ~~Input System의 update mode를 `ProcessEventsInFixedUpdate`로 통일한다.~~ **철회(2026-09-20).** 아래 사유 참조.
- `FighterMatch.StepFrame()`을 `FrameClock` 누적이 아니라 허브의 고정 틱에서 호출한다. `FrameClock`은 재생·테스트용으로 남긴다. 4단계에서 처리한다.

### update mode 전역 통일을 철회한 이유

`FighterInputReader`는 이미 `OnEnable`에서 이전 update mode를 저장하고 `ProcessEventsManually`로 바꾼 뒤 `OnDisable`에서 원래대로 되돌린다.
허브는 **한 번에 한 모듈만 활성**이므로 이 저장·복원이 그대로 모듈 전환 규약이 된다. 전역을 바꿀 필요가 없다.

반대로 전역을 `ProcessEventsInFixedUpdate`로 바꾸면 벤데타·M416·TRG의 마우스 시점 입력까지 60Hz로 샘플링되어 조작 체감이 나빠진다.
격투 하나를 위해 나머지 셋을 손해 보는 교환이므로 하지 않는다. 폴 모듈이 자기 활성 구간에서만 수동 모드를 쓰는 현재 방식이 더 낫다.

대신 4단계에서 확인할 것: 모듈 전환 시 `OnDisable`의 복원이 실제로 실행되는지, 전환 도중 예외가 나면 수동 모드가 남아 다른 직업 입력이 멈추지 않는지.

### 프레임 의존 코드 전수 점검 결과 (2026-09-20)

`Assets/_DCG/Scripts` 전체를 확인했다. **50Hz를 가정한 코드는 없다.**

- `SimulationWorld.FixedUpdate`가 `Time.fixedDeltaTime`을 그대로 넘기고, `ActorSimulation.Step(dt, tick)` 이하 모든 이동·중력·쿨다운·재장전이 `dt` 곱셈으로 처리된다.
- 하드코딩된 `0.02f`는 `VendettaController`의 `Mathf.Max(.02f, tuning.dashSeconds)` 한 곳뿐이며, 0 나눗셈 방지용 하한이지 틱 값이 아니다.
- 증가 연산자는 전부 이벤트 기반(탄약, 발사 수, 명령 시퀀스, 공격 ID)이고 프레임 누적이 아니다.
- 틱 수를 세어 시간으로 쓰는 코드는 없다. `ClientTick`/`ServerTick`은 순서 검증·스냅샷 표시용이다.

따라서 60Hz 전환의 코드 수정 사항은 없다. 남은 것은 수치 체감 재확인과 기존 테스트 회귀뿐이다.

예상 부작용과 대응:

| 부작용 | 대응 |
| --- | --- |
| 프레임당 시간이 0.02 → 0.0167로 줄어 속도·쿨다운·중력 체감이 달라진다 | 수치 자체는 초 단위이므로 이론상 동일하지만, 임시 수치(벤데타 돌진, 총기 반동·연사)는 사람 조작으로 재확인한다. 모두 TuningPending이므로 재조정 자체는 문제가 아니다 |
| 프레임 의존 코드가 있으면 값이 1.2배 어긋난다 | `deltaTime`을 곱하지 않고 프레임마다 누적하는 코드를 전수 점검한다. 발견 시 이번 단계에서 초 단위로 고친다 |
| CPU 부하 20% 증가 | 현재 액터 수에서는 무시 가능. 다만 A* 동기 실행이 틱 안에 있으므로 프로파일로 확인한다 |
| 마우스 시점이 60Hz로 샘플링되어 FPS 계열 체감이 둔해질 수 있다 | 시점·카메라 갱신은 지금처럼 `Update`/`LateUpdate`에 두고 렌더 프레임 델타를 쓴다. 고정 틱으로 내리지 않는다 |
| 기존 EditMode/PlayMode 테스트가 50Hz를 가정할 수 있다 | 0단계 완료 조건에 기존 테스트 전체 통과를 넣는다 |

완료 조건: 기존 5개 랩이 각각 이전과 같이 동작하고, EditMode/PlayMode 전체가 통과하며, 각 랩 스모크가 passed=true.
이 조건을 못 지키면 60Hz 전환을 되돌리고 방향을 다시 정한다. 허브 작업은 그 다음이다.

## 4. 단일 통합 맵 설계

"완전 통합 단일 환경"을 택했으므로 네 직업의 서로 다른 공간 요구를 **하나의 맵이 동시에 만족**해야 한다. 이것이 이번 작업에서 기술적으로 가장 비싼 부분이다.

요구 정리:

| 직업 | 공간 요구 |
| --- | --- |
| 그레이브즈 | 평지 + 정적 엄폐물, A* 그리드 베이크 필요, 탑뷰가 보이는 개방감 |
| 벤데타 | 돌진 6m·투척 10m를 시험할 벽, 고지대, 충돌 테스트 면 |
| M416 | 중근거리 사격선, 엄폐·기울이기 확인용 모서리, 자세 변경용 낮은 엄폐물 |
| TRG | 장거리 시야선(수십~수백 m), 탄도 낙차 확인용 거리 표식 |
| 폴 | 평평하고 장애물 없는 대치 무대, 남쪽에서 북쪽을 보는 카메라 기준축(12 문서 1-1) |

해소 방식 — 한 맵 안에서 기능이 겹치도록 설계한다. 벽으로 나누지 않는다.

- 중앙에 평지 광장을 둔다. 폴의 대치 무대이자 그레이브즈의 기동 공간이다. 무대는 별도 플랫폼이 아니라 바닥 재질로만 구분한다.
- 광장 가장자리에 높이가 다른 엄폐물 군을 배치한다. 그레이브즈의 우회 경로, M416의 자세·기울이기, 벤데타의 충돌 시험을 한 세트가 겸한다.
- 광장에서 한 방향으로 **장거리 레인**을 길게 낸다. TRG의 시야선이자 M416의 사격선이다. 거리 표식을 레인 바닥에 둔다.
- 레인 반대편에 고지대를 둔다. 벤데타의 비행 도착점, TRG의 사격 위치를 겸한다.
- 그리드 베이크는 맵 전체를 한 번에 굽는다. 레인 끝까지 굽으면 셀 수가 커지므로, 그리드 범위는 광장과 엄폐물 구역으로 한정하고 레인은 그리드 밖에 둔다. 그레이브즈는 그리드 안에서만 이동하면 된다. 이 경계를 바닥 표시로 보이게 한다.
- 폴의 카메라 기준축(화면 오른쪽 = 동쪽)을 맵의 동서축과 맞춘다. 맵 전체 좌표계를 이 축 기준으로 잡는다. 장거리 레인은 남북으로 내서 격투 대치축과 겹치지 않게 한다.

표적은 직업별로 요구가 다르므로(정지 표적, 이동 표적, 거리별 표적, 연습 더미) 맵에 고정 배치하지 않고 **활성 모듈이 자기 표적 세트를 생성하고 해제 시 제거**한다.

리스크: 한 맵으로 다섯 조작을 다 만족시키려다 어느 것도 제대로 시험하지 못하는 맵이 될 수 있다. 각 모듈 이식 시 "기존 전용 랩에서 확인하던 것을 이 맵에서 똑같이 확인할 수 있는가"를 완료 조건으로 못 박는다. 못 하면 그 요구만 맵에 추가한다.

## 5. 허브 구조

```
Assets/_DCG/Scenes/ControlHub.unity        (신규)
Assets/_DCG/Scripts/Bootstrap/Hub/
  ControlHubController.cs   씬 수명, 모듈 등록·전환, 틱·카메라·커서·입력맵 소유
  IControlModule.cs         모듈 계약
  ControlModuleBase.cs      공통 구현
  ClassSelectScreen.cs      직업 선택 메뉴
  HubHud.cs                 활성 모듈 HUD 위임 + 공통 표시
  HubSmokeProbe.cs          모듈 순회 자동 점검
Assets/_DCG/Scripts/Bootstrap/Hub/Modules/
  GravesModule.cs  VendettaModule.cs  RifleModule.cs  SniperModule.cs  PaulModule.cs
Assets/_DCG/Scripts/Editor/ControlHubSetup.cs   맵·프리팹·씬 생성, 허브 빌드
```

모듈 계약(초안):

```
IControlModule
  ClassId Id
  string DisplayName
  CursorMode RequiredCursor          Free / Locked
  TickPolicy RequiredTick            Automatic / HubDriven
  void Activate(HubContext context)  액터·표적 생성, 입력맵 enable, 카메라 리그 부착
  void Deactivate()                  생성물 제거, 입력맵 disable, 리그 해제
  void ResetState()                  씬 재로드 없이 초기화
  void TickFixed(uint frame)         고정 틱에서 필요한 모듈만 (폴)
  void UpdateView(float deltaTime)   기존 LabController의 표현 갱신 이식분
  void DrawHud()                     기존 OnGUI 이식분
```

`HubContext`가 제공하는 것: `SimulationWorld`, 공용 `Camera`, `InputActionAsset`, ActorId 발급기, 맵의 기준 좌표(광장 중심, 레인 시작점, 고지대, 격투 무대 두 지점).

원칙:
- 모듈은 서로를 참조하지 않는다. 허브만 안다.
- `DCG.Gameplay`는 지금처럼 `DCG.Classes`를 참조하지 않는다. 의존 방향(05 문서 8절)을 바꾸지 않는다.
- 기존 `XxxLabController`의 **표현·HUD 코드는 그대로 옮긴다**. 이번 작업에서 조작 동작을 고치지 않는다. 동작 변경과 구조 변경을 한 번에 섞으면 회귀 원인을 못 찾는다.
- 기존 5개 랩 씬과 랩 컨트롤러는 **삭제하지 않는다**. 허브가 검증을 통과할 때까지 회귀 비교 기준으로 남긴다. 제거 여부는 통합 완료 후 별도로 기록한다.

전환 흐름:
1. `Bootstrap` → `ControlHub` 진입(`BootstrapEntry`의 고정 로드 대상을 바꾼다).
2. `ClassSelectScreen` 표시. 커서 자유, 모든 게임 입력 맵 disable, `UI` 맵만 enable.
3. 직업 선택 → `Activate` → 플레이.
4. Esc로 선택 화면 복귀 → `Deactivate` → 다시 선택.
5. F5는 씬 재로드가 아니라 활성 모듈 `ResetState()`.

#### 실패 1 — `PaulTests.MacrosDoNotBecomeSinglePunchAndInputSettingsRestore` (해결)

`Assert.That(Time.fixedDeltaTime, Is.EqualTo(.02f)...)`로 50Hz를 리터럴로 박아둔 단언이었다.
이 테스트의 본래 의도는 "폴의 루프가 전역 `fixedDeltaTime`을 바꿔놓고 복원하지 않는 일이 없어야 한다"이므로,
`originalMode`와 같은 방식으로 `Setup`에서 `originalFixedDelta`를 저장하고 그 값과 비교하도록 고쳤다.
이제 전역 틱을 무엇으로 정하든 테스트가 따라온다. 수정 후 통과.

#### 실패 2 — `SceneIntegrationTests.NewInputSystemMouseClickActivatesOverlayWithoutGameplayCommand` (60Hz와 무관, 해결)

`SimulationTests.cs:152`의 `Assert.That(overlay.PatrolActive(), Is.True)`가 False.

**60Hz 때문이 아니다.** Fixed Timestep을 0.02로 되돌리고 같은 테스트를 다시 돌려 확인했다.
0.02에서 `PaulTests`는 통과하고 이 테스트는 그대로 실패했다. 즉 이 건은 전환 이전부터 깨져 있던 기존 결함이다.
08 문서의 2026-09-17 기록은 PlayMode 9/9였고 현재는 51개이므로, 그 이후 M416·TRG·폴 작업 중 어느 시점에 깨진 것으로 보인다.

조사 중 확인한 사실:
- 클릭 좌표는 정상이다. 테스트의 `(250, Screen.height-310)`은 `DebugOverlay`의 patrol 버튼 사각형 `(184,295,148,30)` 안에 들어간다.
- 같은 테스트의 `BlocksPointer` 단언은 통과한다. 즉 오버레이 위라는 판정까지는 맞다.
- `PatrolActive`가 null이면 NullReference가 났을 것이므로 `LabController`의 델리게이트 연결 자체는 되어 있다.
- 따라서 `GravesInputReader.PollInput`이 UI 클릭을 발신하지 못한 것이다. 유력한 후보는 `uiClick.WasPressedThisFrame()`이 아니라
  `point.ReadValue<Vector2>()`다. 테스트는 `mouse.position`으로 `BlocksPointer`를 검증하지만 `PollInput`은 액션 값을 읽으므로,
  합성 장치의 Point 액션이 갱신되지 않았다면 `screen`이 (0,0)이 되어 `IsPointerBlocked`가 false가 되고 UI 클릭이 발신되지 않는다.

**실제 원인 (계측으로 확정).** `GravesInputReader.PollInput`의 조기 반환 지점에 임시 로그를 넣어 돌린 결과:

```
focused=True map=True actor=True init=True
screen=(3569.81, -709.06) click=True cancel=False blocked=False
```

`click=True`이므로 UI 클릭 액션은 정상 인식됐다. 문제는 `screen`이다.
`(3569.81, -709.06)`은 합성 마우스가 아니라 **사용자의 실제 마우스가 있는 멀티모니터 데스크톱 좌표**다.

`Point` 액션은 `<Mouse>/position`에 바인딩되어 있으므로, 마우스 장치가 둘이면 액션이 어느 쪽 값을 돌려줄지 보장되지 않는다.
테스트는 `mouse.position.ReadValue()`로 `BlocksPointer`를 검증하지만 `PollInput`은 액션 값을 읽으므로 둘이 어긋났다.
그 결과 `blocked=False`가 되어 UI 클릭이 발신되지 않았다.

이것이 이 테스트가 **배치 모드에서는 통과하고 에디터에서는 실패한** 이유다.
`Verify-Dcg.ps1`은 `-batchmode -nographics`로 돌리므로 실제 마우스 장치가 없다.
08 문서의 2026-09-17 기록이 통과였던 것도 배치 실행이었기 때문이고, 그 사이에 코드가 깨진 것이 아니다.
즉 이 테스트는 실행 환경에 따라 결과가 달라지는 상태였고, 커서 위치에 따라 배치 모드에서도 언제든 달라질 수 있었다.

**수정.** 테스트가 자기 합성 장치를 격리하도록 고쳤다. 기존 `Mouse` 장치를 전부 `RemoveDevice`한 뒤
합성 장치를 추가하고, `finally`에서 `AddDevice`로 되돌린다.
`DisableDevice`로는 부족하다 — 비활성화해도 액션이 그 값을 계속 반환하는 것을 계측으로 확인했다.

수정 후 같은 계측에서 `screen=(250.00, 770.00) click=True blocked=True`로 바뀌었고 테스트가 통과한다.

#### TimeManager 자산 형식 변경 (중요)

Unity 6000.5.5f1은 `TimeManager.asset`을 `serializedVersion: 2`로 마이그레이션하며 Fixed Timestep을 **유리수**로 저장한다.

```
Fixed Timestep:
  m_Count: 2352000
  m_Rate: { m_Denominator: 1, m_Numerator: 141120000 }
```

`141120000 / 2352000 = 60` 정확히 60Hz다. 부동소수점 오차가 없다.

이 때문에 **이 자산은 손으로 편집하면 안 된다.** 실제로 파일에 `Fixed Timestep: 0.02`를 다시 써넣어도 에디터는
메모리 값을 유지했고 저장 시 덮어썼다. 틱 설정 변경은 반드시 Edit > Project Settings > Time에서 하고,
File > Save Project로 자산에 반영한다. 0단계의 최종 값도 이 경로로 적용했다.
