## 1. 확정 범위와 개발 원칙

각 플레이어가 네 직업 중 하나를 선택해 같은 3D 전장에서 싸우는 1대1 멀티플레이 게임을 만든다. 격투가와 철권 조작은 이번 구현에서 제외한다.

| 직업 ID | 시점 / 무기 | 재현 기준 | 구현의 중심 |
|---|---|---|---|
| Graves | 탑뷰 / 샷건 | 리그오브레전드 그레이브즈 | 마우스 목적지 지정, A* 경로 이동, 타깃 공격과 이동 명령 전환 |
| Vendetta | 3인칭 / 근접무기 | 오버워치 벤데타, 원작 1인칭을 3인칭으로 전환 | 원작 이동·공격 입력과 행동 연결, 별도로 설계할 3인칭 카메라 |
| Rifle | 숄더뷰 / 돌격소총 | 배틀그라운드 M416 | 직접 이동, 시점 조작, 조준 방식 전환, 연사와 반동 |
| Sniper | 1인칭 / 저격총 | 서든어택 TRG | 직접 이동, 스코프 조작, 단발 사격과 후속 행동 |

위 표의 세부 구현 항목은 구현 대상 목록이며, 원작의 정확한 수치와 입력 규칙을 모두 확인했다는 의미는 아니다.

- 조작은 원작을 기준으로 재현한다. 공통 WASD 조작이나 공통 회피 버튼으로 통일하지 않는다.
- 카메라만 다른 네 개의 같은 캐릭터가 아니라, 서로 다른 명령 체계와 전투 리듬을 가진 캐릭터를 구현한다.
- 공통 기반은 이동 충돌, 개체 식별, 체력, 피해, 경기 진행, 네트워크 판정이다.
- 직업별 입력, 카메라, 타깃 선택, 조준, 공격 상태 전환과 입력 취소 규칙은 각 직업이 소유한다.
- 기본 공격만 만드는 단계는 중간 검증 단계다. 원작 조작 재현의 완료로 간주하지 않는다.
- 원작 조작을 변경하는 밸런스 조정은 별도 기획 결정으로 기록한다.
- 벤데타의 3인칭 전환은 사용자가 지정한 예외다. 원작의 1인칭 카메라를 그대로 재현하지 않는다. 전환에 필요한 카메라·조준 규칙은 별도 명세로 정하고, 애매한 기능은 구현하지 않는다.
- 첫 구현은 PC 키보드·마우스를 대상으로 제안한다. 게임패드·모바일·매치메이킹·랭크·상점은 후속 범위다.

## 3. 원작 조작 명세를 먼저 고정한다

각 직업에 대해 다음 표를 원작 화면 녹화, 입력 기록, 사용자 확인으로 채운다. 다른 게임의 관행으로 빈칸을 추측하지 않는다.

| 명세 항목 | 기록할 내용 |
|---|---|
| 기준 환경 | 게임 이름·버전·플랫폼, 기본 키 설정 또는 사용자 지정 설정 |
| 입력 | 키, 누름/유지/뗌, 조합키, 토글/홀드, 동시 입력 우선순위 |
| 이동 | 이동 방향 기준, 가속·감속, 방향 전환, 정지, 장애물 대응 |
| 카메라 | 위치, 시야각, 회전 한계, 감도, 확대·축소, 고정/자유 상태 |
| 공격 | 시작 조건, 준비 시간, 발사/타격 시점, 후딜, 반복 여부 |
| 연결 | 이동 중 공격, 공격 중 이동, 재장전 중 입력, 무기 전환, 취소 가능 시점 |
| 자원 | 탄약, 재장전, 쿨다운 등 해당 원작에 존재하는 규칙 |
| 검증 | 같은 입력을 했을 때 기대되는 상태 변화와 영상 비교 결과 |

직업별 확인 목록:

- **그레이브즈:** 지면/적/공격 불가능한 대상 클릭의 구분, 공격 이동, 정지·유지, 사거리 밖 타깃 추적, 시야에서 사라진 타깃 처리, 공격 준비·발사·후딜과 이동 명령의 관계, 탄 관리와 재장전, 스킬 입력 및 카메라 고정/해제. 이동은 사용자가 지정한 A* 요구를 따른다.
- **벤데타:** 오버워치 벤데타로 확정. 원작 이동·기본 공격·기술·행동 연결의 입력과 규칙을 확인한다. 락온, 회피, 가드, 약/강공격, 콤보 등을 다른 근접 게임에서 가져오지 않는다. 확인되지 않은 기능은 구현하지 않는다. 3인칭 전환의 카메라 거리·피벗·조준 기준·벽 충돌은 원작 규칙과 분리한 설계 항목으로 둔다.
- **M416:** 허리 사격·조준·ADS의 입력 관계, 클릭/유지 설정, 사격 모드, 반동과 탄 퍼짐, 자세·이동·기울이기, 재장전과 행동 중단, 탄도와 장애물 판정.
- **TRG:** 정확한 무기 변형, 스코프 단계와 해제 조건, 비조준/이동 사격, 격발 후 준비 과정, 무기 전환과 재장전 연결, 점프·앉기 등 원작 이동 입력.

반동·이동속도·사거리처럼 미확인인 값은 `TuningPending`으로 표시한다. 테스트용 임시값과 원작 비교를 통과한 값을 구분한다. 전체 재현 범위에 들어가는 스킬과 보조 무기 동작은 이 목록을 기준으로 후속 작업에 포함한다.

## 4. 전체 모듈 구조

```text
로컬 소유 플레이어
  Input Actions
      → 직업별 InputReader
      → 직업별 명령 해석
          ├─ Graves: 목적지 / 타깃 / 공격 이동 / 정지
          └─ 나머지: 이동 입력 / 조준 / 공격 / 직업별 행동
      → CommandGateway
          ├─ 로컬 테스트: LocalSession
          └─ 멀티플레이: NetworkSession → 서버 검증

공통 시뮬레이션
  ActorSimulation
      ├─ 직업별 명령 상태 / 이동 정책
      ├─ CharacterMotor: 최종 이동·충돌
      ├─ CombatController: 공격·재장전·행동 제한
      ├─ HitResolver → DamageSystem → HealthState
      └─ MatchRules: 사망·승패·라운드

표현
  시뮬레이션 결과 → Animator / VFX / Audio / HUD
  로컬 소유자만 → 직업별 CameraRig / 커서 / 입력
  원격 플레이어 → 수신 상태 보간 / 월드 모델 표시
```

### 4.1 책임 경계

| 모듈 | 책임 | 넣지 않을 책임 |
|---|---|---|
| InputReader | 장치 입력과 버튼 전이를 수집 | 직접 위치 변경, 피해 확정 |
| ClassCommandController | 입력을 해당 직업의 명령으로 해석 | 네트워크 전송 API 직접 호출 |
| CommandGateway | 로컬/네트워크 실행 경로 선택 | 무기별 전투 규칙 |
| ActorSimulation | 틱 순서와 직업 구성요소 실행 | UI, 카메라 참조 |
| MovementPolicy | 경로 추종 또는 직접 이동의 요구 속도 생성 | Transform 직접 변경 |
| CharacterMotor | 속도·중력·충돌·지면 상태로 최종 위치 결정 | 목표 선택, 공격 버튼 해석 |
| CombatController | 행동 시작 조건, 시간, 탄약, 취소·연결 규칙 | 카메라 연출에 의존한 피해 타이밍 |
| HitResolver | 총알·타격 형상과 대상의 충돌 검사 | UI 체력 표시 |
| DamageSystem | 피해 적용, 중복 타격 방지, 사망 발생 | 원시 입력 읽기 |
| Presentation | 카메라·애니메이션·소리·HUD | 서버 체력 수정 |
| MatchController | 선택·스폰·경기·승패·재시작 | 개별 무기 반동 구현 |

인터페이스는 실제로 교체가 필요한 경계에 둔다. 모든 클래스에 인터페이스를 붙이지 않는다. 우선 `IMovementPolicy`, `IPathService`, `ICommandGateway`와 직업별 카메라 계약이면 충분하다.

### 4.2 핵심 데이터 계약

| 데이터 | 주요 필드 | 설계 규칙 |
|---|---|---|
| CommandEnvelope | ActorId, Sequence, ClientTick, CommandType | 서버가 발신자 소유권과 중복 여부 검증 |
| MoveToCommand | Destination | 그레이브즈 목적지 명령. 경로 배열을 클라이언트 권위로 신뢰하지 않음 |
| TargetCommand | TargetActorId, OrderType | AttackTarget와 AttackMove를 구분 |
| DirectControlFrame | MoveAxes, AimYawPitch, HeldButtons, PressedButtons | 연속 입력과 단발 버튼 전이를 구분 |
| ActionCommand | ActionId, TargetId 또는 TargetPoint | 직업별 기술·행동. 필요 없는 필드는 사용하지 않음 |
| ActorSnapshot | ServerTick, LastProcessedSequence, Position, Velocity, Facing, LifeState, ActionState, Ammo, Health | 권위 상태와 입력 확인 번호를 함께 전달 |
| CombatEvent | EventId, ActorId, ActionId, StartTick, ImpactData | 중복 연출 방지. 상태 스냅샷을 대체하지 않음 |

명령 데이터에 Camera, Animator, GameObject 참조를 넣지 않는다. 네트워크에서는 식별자와 수치로 전달한다. 실제 전송 구조는 직업별로 필요한 필드만 직렬화한다.

### 4.3 상태와 시간

`생존 상태`, `이동 상태`, `전투 행동 상태`를 나눈다. 걷는 중 사격하거나 앉은 상태로 재장전하는 조합을 하나의 거대한 enum으로 만들지 않는다.

- 생존: Alive / Dead.
- 이동: Grounded / Airborne 및 원작에서 확인된 자세 상태.
- 행동: Ready / Windup / Active / Recovery / Reload 등 직업에 필요한 상태.
- 행동마다 이동 허용, 조준 허용, 다음 입력 예약, 취소 가능 구간을 데이터와 코드로 명시한다.
- 경로 이동 상태는 Idle / MoveTo / ChaseTarget / AttackMove로 분리한다.
- 피해 판정 시점은 시뮬레이션 시간에 둔다. 애니메이션 이벤트는 효과음 등 연출에 사용하고 서버 판정의 유일한 근거로 쓰지 않는다.

`Update`는 입력 수집, 고정 시뮬레이션 틱은 이동·전투, `LateUpdate`는 카메라와 보간된 표현을 담당하도록 설계한다. 단발 입력은 큐에 보관해 틱 사이에서 유실되거나 두 번 소비되지 않게 한다. 시뮬레이션과 물리 실행 순서는 한 곳에서 관리하며 FixedUpdate와 별도 네트워크 틱에서 이동을 이중 실행하지 않는다.

## 5. 이동과 조준 구현

### 5.1 그레이브즈: A* 목적지 이동

초기 전장은 평면 중심의 3D 경기장으로 제안한다. 캐릭터 반지름을 고려한 이동 가능 그리드를 굽고 A*로 경로를 구한다. 이는 원작 내부 구현을 단정하는 것이 아니라 사용자의 A* 요구를 충족하는 구현 선택이다.

```text
마우스 클릭 → UI 클릭 제외 → 지면/타깃 판별
  지면: MoveToCommand → 목적지 유효성 검사 → A* → 경로 단순화
  타깃: AttackTarget → 사거리·시야 확인 → 필요하면 접근 경로 탐색
경로 추종 속도 → CharacterMotor → 실제 이동
```

- `GridGraph`: 정적 통행 가능 영역, 경사·높이 차 허용 기준, 벽 여유 거리.
- `AStarPathService`: 시작/끝 보정, 대각선 모서리 끼어들기 금지, 탐색 예산, Complete/Partial/Unreachable 결과.
- `PathFollower`: 다음 지점 선택, 감속·도착 판정, 정체 감지, 막혔을 때 재탐색 요청.
- `GravesOrderController`: 이동/공격/공격 이동/정지의 우선순위와 전환.
- `TargetTracker`: 유효한 타깃의 현재 위치와 마지막으로 허용된 정보만 제공.

새 클릭은 이전 경로 요청을 대체하며, 오래된 비동기 결과는 요청 번호로 폐기한다. 적이 움직일 때 매 프레임 A*를 재실행하지 않고 이동량·경로 무효화·재탐색 주기 조건을 둔다. 다른 캐릭터와의 충돌은 Motor가 처리하고 정체가 지속될 때 재탐색한다. 첫 버전에서는 동적 장애물과 복층 길찾기를 제외한다.

사거리 밖 적을 추적할 때 목적지는 적의 중심이 아니라 공격 가능한 접근 지점으로 계산한다. 최종 경로와 공격 가능 여부는 서버가 검증한다. 공격 준비 중 이동 명령이 들어왔을 때 취소할지, 발사 후 이동을 예약할지는 원작 명세로 결정한다.

`NavMeshAgent`를 붙였다는 이유로 A* 요구가 완료되었다고 처리하지 않는다. 다른 경로 솔루션으로 바꾸려면 A* 요구, 경로 품질, 서버 실행 가능성을 별도로 확인한다.

### 5.2 직접 이동 직업

직업별 `DirectMovementPolicy`가 카메라 기준 또는 원작 기준 이동 방향을 계산한다. 최종 충돌은 그레이브즈와 같은 Motor가 담당한다. 초기 Motor는 CharacterController 기반 후보로 두고, 필요한 경사·계단·공중 이동·충돌 결과를 검증한다.

동일한 Transform을 CharacterController, Rigidbody, Root Motion, NetworkTransform이 동시에 제어하지 않도록 위치 작성자를 정한다. 서버 시뮬레이션 루트와 클라이언트 표현 루트를 분리한다. 근접 공격의 전진량은 원작에 맞춘 시간별 이동 데이터로 Motor에 전달하고, Animator가 임의로 서버 위치를 움직이지 않도록 한다.

### 5.3 직업별 카메라와 조준

| CameraRig | 구성 | 검증해야 할 위험 |
|---|---|---|
| TopDownRig | 탑뷰, 커서 월드 투영, 원작 기준 화면 이동/고정 | 벽·천장 가림, UI 클릭의 이동 오작동 |
| ThirdPersonRig | 오버워치 벤데타를 위한 3인칭 카메라. 거리·피벗·조준 기준은 미정 | 원작에 없는 락온 등 임의 조작 추가 금지 |
| ShoulderRig | 어깨 시점, 원작 조준 상태별 위치·FOV | 카메라에서는 보이지만 총구 앞은 벽인 경우 |
| FirstPersonRig | 눈 위치, 스코프, 로컬 무기 표시 | 자기 몸 가림, 월드 총구와 화면 조준 차이 |

CameraRig와 AudioListener는 로컬 소유자만 활성화한다. 화면 밖 상대를 어떻게 표시할지는 별도 시야 정책에서 처리한다. 원격 캐릭터는 3인칭 월드 모델로 표시하며, 저격수의 로컬 1인칭 무기 모델은 피해 판정 대상에서 제외한다.

숄더뷰·1인칭은 카메라 조준선으로 목표점을 구한 다음 실제 발사 원점에서 그 지점으로 공격을 계산한다. 발사 원점 앞 벽을 반드시 검사한다. 카메라 Transform을 서버에 그대로 믿고 사용하지 않고 허용된 자세·위치·조준 방향에서 검증한다.

벤데타는 원작의 공격 방향과 실제 타격 범위를 캐릭터 기준으로 유지하는 것을 설계 원칙으로 둔다. 카메라가 뒤로 이동했다고 공격 범위를 늘리지 않는다. 3인칭에서 화면 중심과 실제 공격 방향을 어떻게 맞출지는 별도로 검증한다. 이 관계가 불명확한 상태에서는 임의의 락온이나 자동 방향 보정을 구현하지 않는다.

## 6. 전투 구조

피해 적용은 공통으로 두되 공격 판정 방식은 무기별로 나눈다.

| 공격 모듈 | 담당 | 기준 |
|---|---|---|
| GravesAttackController | 타깃 기반 공격, 준비·발사·후딜, 탄 관리 | 원작의 명령 전환과 발사 형태 확인 |
| ShotgunResolver | 여러 탄/펠릿의 충돌과 동일 대상 피해 집계 | 산탄 개수·분포·차단·피해 합산을 데이터화 |
| RifleWeaponController | 사격 모드, 연사 간격, 반동, 재장전 | M416 명세 |
| BallisticResolver | 이동하는 탄의 궤적과 구간 충돌 | M416 원작 재현에 필요한 탄속·낙차 확인 |
| SniperWeaponController | 스코프·격발·후속 준비·재장전 | TRG 명세 |
| HitscanResolver | 즉시 선분 판정 | TRG 기준 확인 후 채택 여부 확정 |
| MeleeActionController | 원작 근접 공격 연결과 이동 제한 | 오버워치 벤데타에서 확인한 동작만 구현 |
| MeleeSweepResolver | 공격 활성 구간의 형상 이동 검사 | 한 공격이 같은 대상에게 중복 피해를 주지 않게 관리 |

모든 총기를 공통 Raycast 한 줄로 최종 구현하지 않는다. 첫 동작 실험에서 임시 판정을 쓰더라도 원작 탄도와 공격 규칙을 대체한 것으로 기록한다.

`DamageRequest`에는 공격자, 피해자, ActionId, 공격 인스턴스 ID, 충돌 위치·부위, 판정 틱을 넣는다. 서버가 탄약·공격 간격·생존 상태를 검증한 공격만 DamageSystem에 전달한다. 클라이언트는 피해량이나 명중 대상을 확정해 보내지 않는다.

원작 반동의 시각적 흔들림과 실제 탄 방향 변화를 분리해 명세화한다. 난수가 필요한 발사는 서버가 재현할 수 있는 발사 시퀀스와 시드 규칙을 사용한다. 이동속도나 연사 속도를 렌더 프레임 수에 종속시키지 않는다.

## 7. 멀티플레이 구조와 검증 관문

### 7.1 첫 연결 방식

처음에는 호스트 1명 + 클라이언트 1명의 직접 연결로 시작한다. 연결 경로와 게임 규칙을 분리해 이후 Relay나 전용 서버를 붙일 수 있게 한다. 첫 버전의 호스트 이탈은 경기 종료로 처리하고 호스트 이전은 구현 범위에서 제외한다.

Netcode for GameObjects + Unity Transport를 첫 검증 후보로 둔다. 패키지 버전은 프로젝트 호환성 확인 뒤 고정한다. Multiplayer Center가 존재하는 것과 게임 네트워크 런타임이 구현된 것은 구분한다.

주의할 점: 확인한 NGO 2.4 문서는 anticipation을 제공하지만 완전한 rollback/replay 방식의 prediction/reconciliation은 제공하지 않는다고 명시한다. 따라서 패키지 설치만으로 원작 수준의 원격 이동 반응성이 확보된다고 가정하지 않는다. 채택 버전에서도 기능 범위를 다시 확인한다. [Unity NGO Client anticipation](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.4/manual/advanced-topics/client-anticipation.html)

### 7.2 권위와 동기화

| 항목 | 결정 주체 | 로컬 처리 |
|---|---|---|
| 입력·카메라 | 해당 플레이어 | 입력과 시점은 즉시 반영 |
| 위치·이동 가능 여부 | 서버 | 소유자는 예측/보정 실험, 원격은 보간 |
| 경로·공격 타깃 유효성 | 서버 | 목적지 표시와 이동 시작 표현 |
| 탄약·공격 시작·재장전 완료 | 서버 | 예상 연출 후 확정 상태에 맞춰 보정 |
| 명중·피해·사망·승패 | 서버 | 결과 수신 후 표시 |

연속 이동 입력은 시퀀스와 함께 최신 프레임 및 필요한 최근 입력을 전송한다. 단발 명령은 확인 응답과 중복 방지를 둔다. 버튼 해제 패킷이 유실되어도 사격이 계속되지 않도록 최신 버튼 상태와 입력 타임아웃을 함께 사용한다. 이벤트와 최신 상태 스냅샷을 함께 설계해 이벤트 한 번의 유실로 영구적으로 상태가 어긋나지 않게 한다.

직접 이동은 미확인 입력을 보관하고 서버의 마지막 처리 번호를 기준으로 보정하는 실험을 한다. 그레이브즈는 경로 명령과 최신 목적지 번호를 별도로 관리한다. Unity 물리의 완전한 결정성을 가정하지 않는다. 예측용 충돌과 동적 대상 때문에 발생하는 오차를 계측한다.

### 7.3 사격 지연 보상

TRG 등 빠른 공격은 현재 서버 위치만 검사하면 조준 당시 화면과 결과가 달라질 수 있다. 서버 시간 동기화, 제한된 과거 히트박스 기록, 발사 시각 검증을 기술 검증 대상으로 둔다. 클라이언트가 주장하는 임의의 과거 시간을 허용하지 않는다.

초기 검증에서는 정적 엄폐물만 사용해 과거 캐릭터 히트박스와 정적 벽을 함께 검사한다. 지연 보상 창의 길이, 엄폐 뒤 피격 허용 범위, 투사체의 과거 발사 보상 방식은 비교 실험 후 결정한다. 총알·근접 공격 모두를 같은 되감기 규칙으로 묶지 않는다.

### 7.4 조기 중단/재선택 기준

본격적인 스킬과 애니메이션 확장 전에 RTT 0/50/100/150ms, 패킷 손실 0/1/3% 조건으로 확인한다. 이는 테스트 조건 제안이며 원작 수치나 제품 성능 보장은 아니다.

- 호스트와 원격 클라이언트를 번갈아 사용한다.
- 직접 이동의 보정 거리·빈도, 입력부터 화면 반응까지 시간, 사격 중복·유실을 기록한다.
- 그레이브즈가 새 목적지를 눌렀는데 이전 경로로 되돌아가는지 확인한다.
- 스코프 조준과 서버 명중 결과의 차이를 로그와 화면으로 확인한다.
- 반복적인 순간이동이나 사격 지연이 남으면 네트워크 스택 또는 이동 예측 구조를 재검토한 뒤 콘텐츠를 늘린다.

다음 경로는 `DCG-Project` 내부에 구현 시 생성할 제안 구조다.

```text
Assets/_DCG/

    Bootstrap.unity
    ClassSelect.unity
    ControlLab.unity
    DuelArena.unity
  Scripts/
    Core/              # 식별자, 명령·스냅샷 계약, 공통 시간
    Gameplay/
      Actors/          # ActorSimulation, 생존 상태
      Movement/        # Motor, 이동 정책
      Navigation/      # 그리드, A*, 경로 추종
      Combat/          # 행동, 판정, 피해
      Match/           # 경기 진행
    Classes/
      Graves/
      Vendetta/
      Rifle/
      Sniper/
    Presentation/
      Cameras/
      Animation/
      Audio/
      UI/
    Networking/        # NGO 어댑터, 명령 전송, 스냅샷, 보정
    Bootstrap/         # 구성과 의존성 연결
    Editor/            # 그리드 굽기, 설정 검증
  Input/DCGControls.inputactions
  Data/
    Classes/
    Weapons/
    Movement/
    Cameras/
    Actions/
  Prefabs/
    Actors/
    Cameras/
    Weapons/
    UI/
  Tests/
    EditMode/
    PlayMode/
```

씬 책임:

- `Bootstrap`: 세션, 설정, 서비스 수명 관리. 중복 NetworkManager 방지.
- `ClassSelect`: 네 직업 선택과 준비 상태. 서버가 허용 직업과 스폰 구성을 확인.
- `ControlLab`: 각 직업을 독립적으로 시험하는 로컬 씬. 입력·경로·행동 단계·탄 궤적을 시각화.
- `DuelArena`: 같은 지형에서 모든 조합을 시험. 직업별 별도 월드나 별도 물리 공간을 만들지 않음.

Actor 프리팹 구성:

```text
ActorRoot                 # 시뮬레이션 위치의 소유자
  ActorIdentity / ActorSimulation / CharacterMotor / Health
  ClassRuntime            # 직업별 명령·이동·전투 구성
  Hitboxes                # 서버 피해 판정용
  PresentationRoot        # 보간과 애니메이션 표현
    WorldModel
    WorldWeapon
    VFXAnchors

LocalPlayerRig            # 로컬 소유자에게만 생성
  InputReader
  CameraRig + AudioListener
  LocalWeaponView         # 필요한 직업만
  HUD
```

초기 asmdef는 `DCG.Core`, `DCG.Gameplay`, `DCG.Classes`, `DCG.Presentation`, `DCG.Networking`, `DCG.Bootstrap`, 테스트/에디터로 나눈다. Gameplay는 Core에, Classes는 Gameplay에 의존한다. Networking은 Core/Gameplay 계약을 구현하고, Bootstrap이 직업·표현·네트워크 구현을 연결한다. Gameplay가 NGO를 참조하는 순환 의존을 만들지 않는다.

## 9. 설정 데이터와 입력 자산

ScriptableObject는 공유되는 설정만 보관한다. 현재 체력·남은 탄·진행 중 쿨다운·현재 타깃은 캐릭터별 런타임 상태에 둔다. 같은 직업 두 명이 선택해도 서로의 상태를 덮어쓰지 않아야 한다.

| 설정 | 예시 필드 |
|---|---|
| ClassDefinition | ClassId, 표시 이름, Actor 프리팹, 직업 설정 참조 |
| MovementProfile | 속도, 가속, 회전, 충돌 크기, 원작별 자세 값 |
| CameraProfile | 오프셋, FOV, 감도, 확대 상태, 충돌 거리 |
| WeaponDefinition | 공격 판정 방식, 탄약, 발사 간격, 반동·퍼짐·탄도 설정 |
| ActionDefinition | 준비·활성·후딜 시간, 이동 허용, 취소·연결 조건 |
| ReferenceProfile | 기준 원작·버전·설정, 검증 상태, 비교 자료 위치 |

Input Actions는 `UI`, `Graves`, `Vendetta`, `Rifle`, `Sniper` 맵으로 나눈다. 활성 직업과 필요한 UI 맵만 켠다. Action Map으로 입력을 묶고 활성화하는 방식은 Unity Input System의 Actions 구조를 사용한다. [Unity Input System Actions](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.19/manual/Actions.html)

목적지 클릭과 직접 이동 축을 하나의 Move Action으로 억지로 합치지 않는다. 재바인딩, 감도, 토글/홀드 설정은 로컬 설정으로 보관한다. UI 진입·포커스 상실·사망 때 입력 해제와 커서 잠금 해제를 명시적으로 처리한다.

물리 레이어는 최소 World, CharacterBody, Hurtbox, Projectile, NavigationSurface, LocalViewModel로 분리한다. 월드 모델의 장식 콜라이더나 로컬 무기 모델이 총알과 길찾기를 막지 않도록 충돌 매트릭스를 설정한다.

## 10. 구현 단계와 완료 조건

일정은 원작 명세 확인과 네트워크 기술 검증 후 산정한다. 아래 순서는 작업 의존성을 기준으로 한다.

| 단계 | 주요 결과물 | 완료 조건 |
|---|---|---|
| 0. 기준 고정 | 원작별 입력 명세, 프로젝트 패키지 검증, 기초 구조 | 빈 프로젝트 실행/빌드, 네 직업의 확정·미확정 항목 구분 |
| 1. 공통 기반 | Actor, Motor, 명령 게이트웨이, 체력·피해, ControlLab | 입력 없이 테스트 명령으로 이동·피해·사망 재현 |
| 2. 그레이브즈 최소 루프 | 탑뷰, 지면/타깃 클릭, A*, 접근·공격·정지 | 장애물 우회, 경로 교체, 타깃 이동과 공격 명령 전환 정상 |
| 3. M416 최소 루프 | 직접 이동, 숄더 카메라, 조준, 사격·재장전 | 반동·조준·총구 벽 판정과 이동 중 공격 확인 |
| 4. 조기 네트워크 검증 | 그레이브즈 대 M416, 두 실행 인스턴스 | 원격 입력·경로·발사·피해·사망 일치, 지연 계측과 스택 채택 판단 |
| 5. 원작 조작 확장 | 그레이브즈·M416 상세 명세 구현, TRG 추가 | TRG 스코프·발사·후속 입력과 세 직업의 원작 비교 통과 |
| 6. 벤데타 구현 | 오버워치 벤데타의 확인된 조작, 별도 설계한 3인칭 카메라 | 원작 이동·공격 연결 재현, 3인칭 조준·원격 타격 검증. 미정 동작은 제외 |
| 7. 대전 완성 | 직업 선택, 스폰, 승패, 재경기, 10개 대진 | 네 직업으로 1대1 전체 흐름 완료 |
| 8. 품질 보강 | 애니메이션·사운드·HUD, 성능·지연 개선 | 원작 조작 체크리스트와 회귀 테스트 유지 |

벤데타의 원작은 오버워치로 확정되었다. 세부 입력 검증과 3인칭 카메라 명세는 단계 0부터 진행한다. 불명확한 부분은 구현하지 않고 그레이브즈·M416·TRG와 벤데타의 확인된 부분을 진행한다. 미구현 항목을 완료로 처리하지 않는다.

첫 playable의 범위는 그레이브즈 대 M416이다. 목적지 명령 방식과 직접 조작 방식이 함께 동작하는지 가장 먼저 검증할 수 있기 때문이다. 이것으로 네 직업 구현을 완료했다고 처리하지 않는다.

## 11. 테스트와 디버깅

### 자동 검증

- A*: 도달 불가, 좁은 통로, 대각선 코너, 시작점 벽 내부, 새 요청 후 오래된 결과 폐기.
- 명령: 공격 중 이동 입력, 동일 명령 중복, 오래된 시퀀스, 포커스 상실 때 버튼 해제.
- 전투: 탄 부족, 재장전 중 발사, 공격 간격, 같은 근접 공격의 중복 피해, 사망 후 공격 거절.
- 설정: 같은 ScriptableObject를 사용하는 두 캐릭터의 체력·탄약 분리.
- 멀티플레이: 타인 Actor 조작 거절, 중복 발사 방지, 스폰/재시작 시 런타임 상태 초기화.

### 수동 플레이 검증

- 원작과 같은 입력 시퀀스를 수행하고 이동 시작·정지, 공격 발생, 후속 입력 반영을 영상으로 비교한다.
- 네 직업의 서로 다른 조합 6개와 동직업 4개, 총 10개 대진을 시험한다.
- 각 대진에서 호스트/클라이언트 역할과 스폰 위치를 바꾼다.
- 동일 테스트를 서로 다른 렌더 프레임 조건에서 수행해 연사·이동·입력 유실 차이를 확인한다.
- 마우스 UI 클릭, Alt-Tab, 죽은 직후 입력, 재경기 직후 카메라/AudioListener 중복을 확인한다.

디버그 오버레이에는 직업, 현재 명령, 타깃 ID, 경로 상태, 이동·행동 상태, 탄약, 서버 틱, 마지막 확인 시퀀스, RTT, 위치 보정량을 표시한다. 개발용 정보는 최종 플레이 HUD에서 분리한다.

## 12. 남은 기획 결정과 다음 작업 묶음

먼저 확인할 결정:

1. 오버워치 벤데타의 기준 버전·입력 설정·참고 영상, 3인칭 카메라 거리·피벗·조준 규칙. 원작과 3인칭 전환은 확정이며 애매한 세부 기능은 구현하지 않음.
2. 각 원작의 기준 버전과 키 설정. 특히 TRG 변형, M416 조준 입력 설정.
3. 그레이브즈의 스킬·카메라 자유 이동 등 전체 재현 범위. 최소 루프 이후 누락 없이 작업 목록에 반영.
4. 첫 전장의 높낮이·점프 경로·엄폐물 구성. 초기 제안은 정적 엄폐물이 있는 평지 중심 경기장.
5. 탑뷰의 벽 뒤 상대 표시, 타깃 추적 중 시야 상실, 소리 정보 등 공통 전장에서 충돌하는 규칙.
6. 승리 조건과 재경기 규칙. 프로토타입 제안은 상대 사망 시 라운드 종료.

바로 착수할 첫 작업 묶음:

- `DCG-Project` 패키지·입력·렌더 설정 확인과 기본 실행/빌드.
- `_DCG` 폴더, 최소 asmdef, Bootstrap/ControlLab 생성.
- Actor 식별자, 명령 계약, 로컬 CommandGateway, 단일 Motor 구현.
- 그레이브즈의 마우스 지면 클릭, A* 탐색, 경로 표시, 정지·새 명령 처리.
- 장애물 우회와 연속 클릭 검증 후 타깃 접근·기본 공격 추가.

이 작업 묶음이 끝나면 화면상 캐릭터가 움직인다는 것뿐 아니라, 명령 해석·경로·이동·전투가 분리되어 이후 직업과 네트워크를 붙일 수 있는 상태를 확인한다.
